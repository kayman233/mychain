**Важная тема: детерминизм в блокчейне**

Теперь, когда мы поняли общую архитектуру Cosmos, важно обсудить одно критическое тех-
ническое требование, которое лежит в основе работы любого блокчейна, особенно в контек-
сте BFT-консенсуса. Это требование — детерминизм.

Прежде чем переходить к деталям консенсуса Tendermint, давайте разберёмся, что такое де-
терминизм и почему он так важен.

Что это означает? Одинаковый вход должен давать точно такой же переход состояния на всех
узлах. Это основа репликации состояния в распределённых системах.

**Cosmos (SDK/CometBFT): жёсткое требование**

Спецификация CometBFT явно требует, чтобы ABCI-приложение было строго детерминиро-
ванным. Один и тот же упорядоченный набор транзакций должен дать одинаковый AppHash
и ответы на всех узлах. Если это условие нарушается, консенсус просто не сможет продол-
жаться — узлы начнут расходиться.

Важный нюанс: контроль детерминизма лежит на разработчике. SDK и ваше приложение не
имеют «магической» фазы для автоматического обнаружения недетерминизма. Это достига-
ется дисциплиной разработки: запрет недетерминированных конструкций (случайные числа
без фиксированного seed, обращение к системному времени напрямую), использование оди-
наковых версий зависимостей, тщательное тестирование.

Для смарт-контрактов CosmWasm создаёт максимально детерминированную среду: запрет
операций с плавающей точкой (или нормализация NaN в новых версиях), ограниченный API,
песочница выполнения.

**Сравнение: Hyperledger Fabric**

Для контраста: в Hyperledger Fabric детерминизм «институционально» обеспечен через про-
цедуру execute → order → validate и endorsement policies. Одно и то же предложение тран-
закции выполняют несколько эндорсеров независимо. Если их read/write-наборы расходятся
из-за недетерминизма, транзакция признаётся недействительной на этапе валидации и не
попадает в состояние. То есть недетерминизм ловится до изменения общего ledger.

В Cosmos подход другой: мы полагаемся на то, что приложение изначально детерминирова-
но, и консенсус обеспечивает одинаковый порядок входных данных для всех узлов.

=== СЛАЙДЫ 4-9: TENDERMINT/COMETBFT ===

Теперь переходим к самому интересному — консенсус-протоколу, который лежит в основе
всей экосистемы Cosmos.

**Что такое CometBFT/Tendermint Core**


CometBFT (ранее известный как Tendermint Core) — это лидер-ориентированный Byzantine
Fault Tolerant консенсус-протокол для State Machine Replication (SMR).

Что это означает на практике? На каждой высоте блока H протокол согласует следующий
блок с порогом больше 2/3 голосующей мощности валидаторов и даёт instant finality — мо-
ментальную необратимость решения. Как только узел наблюдает +2/3 precommit (финальное
подтверждение), блок закреплён навсегда, без вероятностных откатов.

Протокол работает в модели partial synchrony (частичной синхронности) — это важное до-
пущение, к которому мы ещё вернёмся. После стабилизации сети прогресс гарантирован.

Внутри протокол представляет собой машину состояний с чёткими переходами: **NewHeight
→ Propose → Prevote → Precommit → Commit**. Спецификация даёт формальные доказа-
тельства двух ключевых свойств: safety (безопасность — не закоммитим разные блоки) и
liveness (живучесть — прогресс не остановится).

**Валидаторы и веса голосов**

В отличие от простого “один узел — один голос”, в CometBFT каждый валидатор имеет
voting power — голосующую мощность. Это может быть количество застейканных токенов
или любой другой показатель, определяемый приложением.

Все кворумы считаются по мощности, а не по количеству узлов. Когда мы говорим “+2/3”,
это означает строго больше двух третей от общей голосующей мощности.

Важный математический факт: любые два кворума +2/3 гарантированно пересекаются по
мощности больше чем на 1/3. Это пересечение — фундамент для safety протокола. Даже если
часть узлов византийские (ведут себя произвольно или злонамеренно), пока их меньше 1/3,
честные узлы в кворумах обязательно пересекутся и не допустят противоречивых решений.

**Модель сети: partial synchrony (частичная синхронность)**

Прежде чем углубляться в протокол, важно понять допущения о сети.

Что такое partial synchrony? Это золотая середина между двумя крайностями: - _Синхронная
сеть:_ есть известная верхняя граница задержки Δ для всех сообщений - _Асинхронная сеть:_
задержки могут быть бесконечными, никаких гарантий

Partial synchrony означает: задержки сообщений могут быть сколь угодно большими в какие-
то периоды времени, но существует момент времени GST (Global Stabilization Time), после
которого задержка ограничена некоторым Δ. Критически: мы не знаем заранее ни когда на-
ступит этот момент, ни чему равно Δ.

Это реалистичное допущение для реальных сетей: бывают периоды нестабильности (атаки,
сетевые проблемы), но в конечном счёте сеть стабилизируется. И протокол должен гаранти-
ровать прогресс после стабилизации.

**Общая картина: как начинается консенсус**

Представьте: у нас уже есть блокчейн на высоте H-1, есть мемпул с транзакциями, ждущими
включения в блок. Нам нужно достичь консенсуса о следующем блоке на высоте H.


```
Протокол организован в раунды. В каждом раунде R происходит попытка согласовать блок.
Если что-то идёт не так (плохой лидер, сетевые задержки), переходим к раунду R+1 с новым
лидером.
```
```
Давайте разберём каждый шаг подробнее:
Шаг 1: Propose (H, R) — предложение блока
```
```
На этом шаге один выбранный валидатор (proposer, или лидер) предлагает блок для высоты
H в раунде R.
```
```
Как выбирается лидер? Используется детерминированный weighted round-robin алгоритм:
```
- Каждый валидатор имеет приоритет, который копится пропорционально его весу (voting
    power) - В начале раунда лидером становится валидатор с максимальным приоритетом - По-
    сле выбора приоритет этого валидатора уменьшается на сумму всех весов (чтобы дать шанс
    другим) - Затем все приоритеты увеличиваются пропорционально весам
    Ключевые требования к этому алгоритму: - **Детерминизм:** все честные узлы должны вычис-
    лить одного и того же лидера для пары (H, R) - **Fairness:** частота лидерства должна быть
    пропорциональна доле голосующей мощности

```
Лидер собирает транзакции из мемпула, формирует блок и рассылает proposal всем валида-
торам.
```
```
Шаг 2: Prevote (H, R) — предварительное голосование
```
```
Получив (или не получив) proposal, каждый валидатор должен отправить prevote — предва-
рительный голос. Это первый этап голосования.
```
```
Правила отправки prevote: 1. Если валидатор locked (залочен) на какой-то блок X (напри-
мер, в предыдущем раунде он уже начал процесс коммита этого блока) → он голосует prevote
за X, даже если получил другое предложение 2. Иначе, если получил и успешно проверил
proposal (валидные транзакции, корректная структура) → голосует prevote за предложенный
блок 3. Иначе (не получил proposal или он невалидный) → голосует prevote за<nil>
Зачем нужен prevote? Это способ «прощупать» сеть: достаточно ли узлов видят и одобряют
этот блок?
Шаг завершается при одном из условий: - Узел собрал +2/3 prevote за один конкретный блок
B (или за<nil>) — это называется PoLC (Proof of Lock Change) для раунда R - Истёк таймаут
prevote
```
```
ЧтотакоеPoLC? Proof of Lock Change — это доказательство того, что более 2/3 сети предва-
рительно одобрили определённое значение (блок или nil) в данном раунде. Это критически
важное понятие для механизма lock/unlock.
```
```
Шаг 3: Precommit (H, R) — финальное голосование
Теперь, основываясь на результатах prevote-фазы, валидаторы отправляют precommit — фи-
нальное подтверждение.
```

Правила отправки precommit: 1. **Если есть PoLC(H, R) за блок B** → валидатор (re)locks на
B и отправляет precommit(B) - Lock означает: “Я теперь обязуюсь поддерживать этот блок в
последующих раундах” - Relock возможен только при наличии PoLC — нельзя просто пере-
думать 2. **Если есть PoLC(H, R) за<nil>** (большинство не увидело годный блок) → unlock
(снимаем предыдущий lock, если был) и отправляем precommit(<nil>) 3. **Иначе** (нет квору-
ма +2/3 ни за что) → сохраняем прежний lock (если был) и отправляем precommit(<nil>)

Шаг завершается при одном из условий: - Собрали +2/3 precommit(<nil>) или истёк таймаут
→ переходим к следующему раунду R+1 с новым лидером - Собрали +2/3 precommit(B) за
один конкретный блок B → переходим к коммиту!

**Зачемнужнасхемаlock/unlock?** Это сердце протокола. Lock гарантирует, что если какой-то
блок «почти закоммитился» (получил +2/3 prevote), честные узлы не смогут внезапно пере-
ключиться на другой блок без веской причины (новый PoLC). Это даёт safety. При этом relock
через PoLC позволяет не застревать навечно — это даёт liveness.

**Шаг 4: Commit (H) → NewHeight (H+1)**

Как только узел видит +2/3 precommit за один BlockID, он знает: этот блок финален.

Что происходит: 1. Узел фиксирует CommitTime (время коммита) 2. Дожидается получения
всех частей блока, если чего-то не хватает 3. Применяет блок к состоянию через ABCI
(Application Blockchain Interface) — вызывает FinalizeBlock 4. Переходит в состояние
NewHeight для следующей высоты H+

В NewHeight: - Сохраняются коммит-подписи в LastCommit (для заголовка следующего бло-
ка) - Выдерживается timeoutCommit (небольшая пауза для синхронизации сети) - Стартует
новый цикл для высоты H+1, раунд 0

**Общие условия выхода (чтобы «не застрять»)**

Протокол предусматривает механизмы для догоняющих узлов:

1. **Skip-ahead:** Узел в любой момент может перескочить на более поздний раунд R’, если
    получил “догоняющие” сообщения, показывающие, что там уже есть +2/3 prevote или
+2/3 precommit. Это помогает выравнивать состояние узлов, даже если кто-то отстал.
2. **Таймауты:** На каждом шаге (propose, prevote, precommit) установлены таймауты. Если
    лидер плохой или сеть тормозит, по истечении таймаута узлы автоматически перехо-
    дят к следующему раунду R+1 с новым лидером. Это критично для liveness в модели
    partial synchrony — без таймаутов можно застрять навечно в ожидании сообщений от
    оффлайн-узла.

_Q: Почему именно кворум +2/3, а не простое большинство >1/2?_

A: Из-за гарантированного пересечения кворумов. Любые два кворума >2/3 пересекаются
более чем на 1/3 общей мощности. Это означает, что если < 1/3 узлов византийские, в каж-


```
дом кворуме будет достаточно честных узлов, которые не позволят принять противоречивые
решения. При кворуме >1/2 два кворума могут не пересекаться вообще.
```
```
Q: Что случится, если ≥ 1/3 валидаторов — византийские?
```
A: Протокол больше не даёт гарантий. Можно нарушить safety (вплоть до двойного коммита
— финализации двух разных блоков на одной высоте) или сорвать liveness (остановить про-
гресс). Это фундаментальное ограничение BFT-протоколов: они терпят до 1/3 византийских
узлов, но не более.

```
Q: Можно ли «обогнать» сеть и получить два разных коммита на одной высоте?
A: Нет, именно благодаря механизму lock и PoLC. Честные узлы не могут переключиться на
другой блок без нового PoLC, а получить два разных PoLC на одной высоте невозможно при
< 1/3 византийцев. Финальный коммит один на высоту.
```
```

```
```
A: Это разные уровни абстракции. Tendermint/CometBFT — это консенсус-протокол, отвеча-
ющий за то, КАК узлы согласуют блоки. Proof-of-Stake — это механизм выбора валидато-
ров и определения их весов (через стейкинг токенов) плюс система стимулов/наказаний. В
Cosmos они работают вместе: PoS определяет валидатор-сет и веса, а Tendermint использует
эти веса для консенсуса.
```
```

```
```
A: В IBC light client-ы на одной цепи проверяют доказательства от другой цепи. Если бло-
ки могут откатываться (как в PoW), нужно ждать глубокого подтверждения и обрабатывать
возможные рассогласования. С мгновенной финальностью: увидели заголовок с +2/3 подпи-
сями — блок финален, можно безопасно обработать пакеты. Нет риска отката уже принятых
межцепочечных транзакций.
```

**Сравнение: Tendermint vs PoW vs PoS (Nakamoto-стиль)**

Теперь давайте посмотрим, чем Tendermint отличается от других популярных механизмов
консенсуса. Важно понимать: мы сравниваем именно консенсус-протоколы, а не механиз-
мы выбора валидаторов. PoW и PoS-Nakamoto — это одновременно и защита от Sybil-атак
(выбор лидера), и консенсус. Tendermint — только консенсус; защиту от Sybil обеспечивает
внешний механизм (обычно PoS).

**1. Финальность**
    - **Tendermint:** Instant finality — +2/3 precommit ￿ блок необратим немедленно
    - **PoW (Bitcoin):** Probabilistic finality — вероятность отката убывает экспоненциально с
       глубиной (k подтверждений), но теоретически никогда не достигает 0
    - **PoS-Nakamoto (базовый):** Также probabilistic; механизмы типа LMD-GHOST/FFG в
       Ethereum дают “экономическую финальность”, но базово всё ещё не мгновенную
**2. Вилки (форки) и откаты**
    - **Tendermint:** Финализированные вилки невозможны при < 1/3 византийских валидато-
       ров; форки на уровне «нефинализированных» раундов возможны, но они не коммитят-
       ся
    - **PoW/PoS-Nakamoto:** Короткие форки — это норма работы сети; выбор «длинней-
       шей/тяжелейшей» цепи может откатить недавние блоки
**3. Задержки и пропускная способность**
    - **Tendermint:** Латентность = один-два раунда (обычно секунды). TPS ограничены раз-
       мером валидатор-сета и сетью (O(n²) коммуникация), но высокая «прикладная» про-
       пускная способность — не нужно ждать k блоков для уверенности в финальности
    - **PoW:** Большие и вариативные задержки из-за вероятностного процесса майнинга.
       Нужно ждать множество подтверждений для практической уверенности
    - **PoS-Nakamoto:** Быстрее PoW (детерминированные слоты), но финальность всё ещё ве-
       роятностная, часто требуется дополнительный “чекпоинтинг” для практической необ-
       ратимости
**4. Энергия и ресурсы**
    - **Tendermint:** Нет Proof-of-Work → энергоэффективен; основная нагрузка — сетевая
       коммуникация и криптографические подписи
    - **PoW:** Энергозатратен по определению — требуется постоянное решение криптогра-
       фических головоломок
    - **PoS-Nakamoto:** Энергоэффективен, как и Tendermint
**5. Модель безопасности (кто может нарушить)**
    - **Tendermint:**
       **-** Safety можно нарушить при ≥ 1/3 голосующей мощности византийских узлов
       **-** Liveness можно нарушить длительными асимметричными сетевыми условия-
          ми/DoS + плохими лидерами, но при partial synchrony liveness восстанавливается
    - **PoW:** Атака 51% хэшрейта позволяет переписывать историю; финальность нестрогая


- **PoS-Nakamoto:** Уязвимости типа “nothing-at-stake”, “long-range attacks” смягчаются
    механизмами чекпоинтов, слэшинга и временных допущений
**6. Децентрализация и размер валидатор-сета**
- **Tendermint:** Практически полезные сети часто ограничивают активный валидатор-сет
сотнями узлов, иначе растут квадратичные сетевые издержки (O(n²) сообщений, под-
писи, госсип). Это компромисс ради производительности
- **PoW:** Открытое участие для любого, кто имеет хэшрейт, но фактическая централиза-
ция происходит в пулах майнинга
- **PoS-Nakamoto:** Участвовать проще, чем в PoW (не нужно специальное оборудование);
реальная децентрализация зависит от распределения стейка
**7. Простота интеграции для приложений**
- **Tendermint:** Приложениям очень удобно — финальность достигается сразу, не нужно
“ждать k блоков”, упрощается межцепочечное взаимодействие через light client-ы (IBC)
- **PoW/PoS-Nakamoto:** Из-за вероятностных откатов приложения вынуждены ждать глу-
боких подтверждений и проектировать идемпотентные сценарии (обработка возмож-
ных откатов)
**8. Ответственность (accountability)**
- **Tendermint:** Естькриптографическиеevidence(DuplicateVoteEvidence,LightClientAttackEvidence);
можно математически доказать и экономически наказать double signing (слэшинг)
- **PoW:** Сложно персонализировать вину — майнеры анонимны, работают через пулы
- **PoS-Nakamoto:** С механизмами слэшинга возможна экономическая ответственность,
но доказательства часто сложнее из-за вероятностной финальности

**Где Tendermint слабее**

Справедливости ради, у Tendermint есть свои ограничения:

1. **Масштабированиенатысячивалидаторов** — квадратичная коммуникация и наклад-
    ные расходы на подписи становятся узким местом
2. **Чувствительностьксетевымусловиям** — для хорошей задержки нужна устойчивая
    p2p-сеть и правильно настроенные таймауты
3. **Операционная дисциплина** — требует надёжной инфраструктуры валидаторов, осо-
    бенно чтобы избежать случайного double signing (который карается слэшингом)

## === СЛАЙДЫ 11-17: IBC (INTER-BLOCKCHAIN COMMUNICATION) ===

Мы подошли к самой, пожалуй, революционной части экосистемы Cosmos — протоколу
межблокчейновой коммуникации IBC.

**Что такое IBC и зачем он нужен**

Вспомните, в начале лекции мы говорили о том, что Cosmos — это не «один чейн для всех»,
а экосистема суверенных блокчейнов. Возникает естественный вопрос: как эти независимые
чейны безопасно общаются между собой?

IBC — это стандартизированный протокол для передачи произвольных данных и активов
между блокчейнами. Ключевое слово здесь — _стандартизированный_. Это не какой-то кон-
кретный мост между двумя чейнами, а универсальный протокол, который может связать лю-
бые чейны, поддерживающие IBC.

**Высокоуровневый принцип работы**

На очень высоком уровне IBC работает так:

1. Каждый блокчейн, желающий взаимодействовать с другим, хранит **light client** этого
    другого блокчейна on-chain
2. Когда нужно передать данные из Chain A в Chain B, Chain A записывает это в своё
    состояние
3. **Релейер** (независимый оффчейн-процесс) видит это событие, забирает данные и дока-
    зательство из Chain A и отправляет транзакцию в Chain B
4. Chain B проверяет доказательство через свой light client Chain A и, если всё корректно,
    обрабатывает данные

Критически важно: релейеру не нужно доверять! Вся проверка происходит криптографиче-
ски через light client.

**Компоненты и участники IBC**

Давайте разберём, из каких частей состоит IBC-архитектура. Она многослойная, и каждый
слой имеет свою роль.

**1. IBC-приложения (модули/контракты)**

На каждой цепи есть on-chain компоненты, которые хотят общаться через IBC. Это мо-
гут быть: - Модули Cosmos SDK (например, x/ibc-transferдля переводов токенов) -
CosmWasm смарт-контракты с IBC-поддержкой

Эти компоненты реализуют специальные IBC-коллбэки: -OnRecvPacket— вызывается при
получении пакета -OnAcknowledgementPacket— вызывается при получении подтвержде-
ния о доставке -OnTimeoutPacket— вызывается, если пакет не был доставлен в течение
timeout

Эти коллбэки — это и есть ваша бизнес-логика: что делать с полученными данными, как
реагировать на успех или неудачу доставки.

**2. Light Client (на цепи-хосте, по одному на контрагентскую цепь)**


Это ключевой элемент безопасности IBC. Для КАЖДОЙ внешней цепи, с которой вы хотите
общаться, вы создаёте on-chain light client этой цепи.

Что такое light client? Это минимальный верификатор, который не хранит полную историю
блоков, но умеет проверять: - Что блок был действительно финализован валидаторами контр-
агентской цепи (через проверку подписей) - Что определённые данные действительно нахо-
дятся в состоянии этого блока (через Merkle-доказательства)

Важные нюансы:

- **Один клиент — много каналов:** Один light client можно переиспользовать для мно-
    жества соединений и каналов к той же внешней цепи. Создавать отдельный клиент для
    каждого канала не нужно.
- **Регулярные обновления:** Light client нужно периодически обновлять, чтобы он знал
    о свежих блоках и валидатор-сете контрагентской цепи. Обычно это делают релейеры,
    отправляя транзакцииMsgUpdateClient.

**Как создаётся light client изначально?**

Это важный вопрос. При первом подключении к новой цепи происходит следующее:

_Где создаётся:_ На целевой цепи (допустим, Chain B хочет получить клиент для Chain A)
через обычную on-chain транзакциюMsgCreateClientв модуле IBC02-client.

_Кто отправляет:_ Обычно релейер или любой оператор, имеющий доступ к узлам обеих
цепей.

_Какие данные нужны:_

1. **ClientState** чужой цепи (Chain A):
    - chain_id— идентификатор цепи A
    - trust_level— например, 1/3 (минимальная доля валидаторов для доверия)
    - trusting_period— период, в течение которого можно доверять клиенту без об-
       новления
    - unbonding_period— период анбондинга стейка в цепи A
    - max_clock_drift— допустимое расхождение часов
    - proof_specs— спецификация для проверки ICS-23 Merkle-доказательств
    - Стартовая доверенная высота
2. **ConsensusState** на конкретной высоте h￿ цепи A:
    - timestamp(h￿)— временная метка блока
    - next_validators_hash(h￿)— хэш валидатор-сета для следующего блока
    - root = AppHash_A(h￿)— корень Merkle-дерева состояния цепи A на высоте h￿

_Откуда берутся эти данные?_ Релейер получает их из полного узла Chain A через RPC:
заголовок финализованного блока h￿, соответствующий commit с подписями валидаторов,
информацию о валидатор-сете. Затем формирует ClientState и ConsensusState и отправляет
MsgCreateClientна Chain B.

После этого light client создан и можно начинать верификацию доказательств!


**3. Connection (соединение поверх пары клиентов)**

Теперь, когда у нас есть light client-ы, мы можем установить Connection — двустороннюю
“рамочную трубу доверия” между Chain A и Chain B.

```
Что такое Connection? Это проверяемая связь между двумя блокчейнами, которая опирается
на пару light client-ов (по одному с каждой стороны).
```
```
Как устанавливается Connection?
```
```
Через процесс рукопожатия (handshake), состоящий из четырёх шагов: 1. INIT (Chain A):
инициация соединения 2. TRY (Chain B): попытка принять соединение, проверка ClientState
от A 3. ACK (Chain A): подтверждение, проверка ответа от B 4. CONFIRM (Chain B): фи-
нальное подтверждение 5. Статус: OPEN — соединение активно
```
```
Каждый шаг включает криптографические доказательства того, что другая сторона действи-
тельно выполнила свою часть рукопожатия. Это гарантирует, что обе стороны согласовали
взаимные проверки состояний.
```
```
Для чего нужно Connection?
```
- Обеспечивает согласованность и безопасность передачи данных между цепями
- Один Connection можно переиспользовать для множества каналов (для разных прило-
    жений)
- Connection остаётся активным, пока поддерживаются оба light client-а

```
Важно: Connections децентрализованы и permissionless — любой может инициировать созда-
ние Connection между цепями.
```
**4. Port (имя маршрута приложения)**

```
Port — это просто идентификатор, который “резервирует” IBC-приложение для себя. Думай-
те о нём как об адресе приложения в рамках IBC.
```
```
Примеры портов: -transfer— стандартный порт для ICS-20 (перевод токенов) -icahost
/icacontroller— для Interchain Accounts - Произвольные порты для кастомных приложе-
ний
Как это работает в SDK и CosmWasm?
```
- **ВCosmosSDK:** модуль привязывает порт через capability-based механизм — получает
    “capability token”, подтверждающий владение портом
- **В CosmWasm:** контракт объявляет поддержку IBC при инстанцировании и автомати-
    чески получает свой порт
**5. Channel (канал для конкретного приложения поверх Connection)**

```
Наконец, Channel — это “логическая труба” для конкретного приложения между двумя це-
пями.
```
```
Для КАЖДОГО приложения, которое хочет общаться с контрагентом, открывается отдель-
ный Channel. У одного приложения может быть несколько каналов — к разным цепям или
даже к одной цепи для разных потоков данных.
```

_Что фиксирует Channel:_

- port_id— какому модулю/контракту доставлять пакеты
- connection_hops— через какие Connection-ы идут данные (обычно один)
- ordering— упорядоченность доставки:
    **- ORDERED** — пакеты обрабатываются строго по порядку (если пакет N не до-
       ставлен, пакет N+1 ждёт)
    **- UNORDERED** — пакеты могут обрабатываться в любом порядке
- version— версия протокола приложения
- counterparty{port, channel}— порт и канал на контрагентской цепи

_Жизненный цикл Channel:_

Как и Connection, Channel создаётся через рукопожатие: 1. **INIT** → **TRY** → **ACK** → **OPEN**

После открытия канала можно отправлять пакеты!

_Создание и отправка пакетов:_

1. **Создание канала:** В каждой цепи создаётся канал, связанный с идентификатором
    Connection. Процесс включает проверку клиентских состояний через существующие
    Connection-ы.
2. **Отправка пакетов:** После того как канал открыт, пакеты передаются между цепями.
    Каждый пакет включает:
       - Данные приложения (payload)
       - Информацию о таймауте (timeout height или timestamp)
       - Sequence number для отслеживания порядка
    Передача включает отправку данных с одной стороны, их получение и верификацию
    на другой, и подтверждение успешного завершения.

_Гарантии безопасности:_

- **Криптографическая верификация:** Каналы используют Merkle-доказательства для
    верификации всех передаваемых данных. Это исключает возможность несанкциони-
    рованного вмешательства или потери данных.
- **Доверенно-независимыерелейеры:** Даже если релейер, передающий пакеты, ненадё-
    жен или злонамерен, сами пакеты и их порядок проверяются light client-ами on-chain.
    Релейер не может подделать или изменить данные — он может только доставить или
    не доставить пакет.
**6. Пакеты и маршрутизация через IBC Core**

Теперь давайте посмотрим, как данные фактически передаются.

_Отправка пакета:_

Когда приложение (модуль или контракт) хочет отправить данные, оно вызывает метод IBC
Core, передавая: -port_id— свой порт -channel_id— канал, через который отправлять -
Данные (payload) - Timeout


На исходной цепи IBC Core: 1. ЗаписываетpacketCommitment— хэш пакета в своё состоя-
ние 2. УвеличиваетnextSequenceSendдля этого канала 3. Эмитит событие (event)

_Релейер видит событие и действует:_

Релейер — это оффчейн-процесс, который мониторит обе цепи. Увидев событие отправки па-
кета, релейер: 1. Получает пакет и Merkle-доказательство его наличия в состоянии Chain A 2.
Формирует транзакциюMsgRecvPacketдля Chain B, включая: - Сам пакет - Доказательство
(proof) - Высоту блока Chain A, на которой пакет был записан (proof_height)

_Получение и маршрутизация пакета:_

На принимающей цепи (Chain B) IBC Core получаетMsgRecvPacket: 1. Проверяет дока-
зательство через light client Chain A — действительно ли этот пакет записан в состоянии
Chain A 2. По(port_id, channel_id)определяет, какому модулю/контракту доставить па-
кет 3. ВызываетOnRecvPacketэтого модуля 4. Модуль обрабатывает данные и возвращает
acknowledgement (подтверждение) 5. IBC Core записывает acknowledgement в своё состояние

Маршрутизация всегда однозначна: **[IBC Core] → (по port/channel) → [нужный модуль]**

_Подтверждение доставки:_

Релейер видит acknowledgement на Chain B и доставляет его обратно на Chain A через
MsgAcknowledgement. IBC Core Chain A вызываетOnAcknowledgementPacketу модуля-
отправителя — теперь он знает, что пакет успешно доставлен и обработан.

**7. Relayers (ретрансляторы) — невоспетые герои IBC**

Важно понять роль релейеров:

- **Не являются частью блокчейна:** Это независимые оффчейн-процессы или сервисы
- **Физически передают пакеты:** Они “носят” данные между цепями, но не имеют вла-
    сти над ними
- **Доверенно-независимы:** Релейерам не нужно доверять! Они не участвуют в проверке
    данных или управлении безопасностью. Вся верификация происходит on-chain через
    light client-ы
- **Permissionless:** Любой может запустить релейер. Это децентрализованная инфраструк-
    тура

Что происходит, если релейер злонамеренный? - Не может подделать данные — они проверя-
ются криптографически - Не может изменить порядок в ORDERED каналах — проверяется
sequence number - Может только не доставить пакет (DoS), но для этого есть механизм timeout

**Полный workflow IBC-транзакции (резюме)**

Давайте соберём всё вместе на примере перевода токенов из Chain A в Chain B:

1. **Подготовка (один раз):**
    - Созданы light client-ы: Chain A имеет клиент Chain B, и наоборот
    - Установлен Connection между A и B
    - Открыт Channel дляtransferприложения
2. **Отправка:**


- Пользователь на Chain A отправляетMsgTransfer(ICS-20)
- Модульtransferблокирует токены и вызывает IBC Core для отправки пакета
- IBC Core записывает commitment, эмитит событие
3. **Релейинг:**
- Релейер видит событие, получает пакет и proof
- ОтправляетMsgRecvPacketна Chain B с доказательством
4. **Получение:**
- Chain B проверяет proof через light client Chain A
- IBC Core маршрутизирует пакет модулюtransferна Chain B
- Модуль создаёт ваучерные токены для пользователя (IOU-представление токенов
Chain A)
- Возвращает acknowledgement
5. **Подтверждение:**
- Релейер доставляет acknowledgement обратно на Chain A
- Chain A знает, что перевод успешен

**Гарантии безопасности IBC**

Подведём итог, какие гарантии даёт IBC:

1. **Безопасность через криптографию:**
    - Вся проверка состояния происходит на уровне light client-ов
    - Используются криптографические доказательства: Merkle-деревья, подписи вали-
       даторов
    - Light client-ы подтверждают, что переданный блок был действительно финализо-
       ван на целевой цепи
2. **Доверенно-независимая архитектура:**
    - Безопасность не зависит от операторов релейеров
    - Безопасность обеспечивается исключительно light client-ами и криптографией
    - Permissionless — любой может участвовать
3. **Изоляция ошибок:**
    - Данные передаются строго между двумя конкретными цепями
    - Проблемы в одной паре цепей не влияют на другие сети экосистемы
    - Каждый Connection и Channel — независимая единица
4. **Мгновенная финальность — критична для IBC:**
    - Помните, почему мы так подробно говорили о Tendermint? Именно instant finality
       делает IBC простым и безопасным
    - Нет риска отката уже принятых и обработанных пакетов
    - Light client-у достаточно увидеть +2/3 подписей — блок финален
